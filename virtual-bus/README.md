# virtual-bus

Virtual buses for running embedded-hal 1.0 I2C / SPI drivers against IC models on your PC.

For an overview, see the repository's `README.md`. For usage, see `examples/` and the API documentation (`cargo doc --open`).

## Source layout

```text
src/
├ lib.rs                  crate docs and re-exports of the common types
├ verilated.rs            RawModel / VTable (runs the models generated by virtual-bus-build)
├ bus/                    bus infrastructure
│  ├ mod.rs               Shared / shared, SimDelay (a DelayNs that advances simulated time)
│  ├ pin.rs               InvertedPin (logical inversion, for active-high CS)
│  ├ i2c/
│  │  ├ mod.rs            VirtualI2cBus, I2cSlave, fault injection, transaction log
│  │  ├ bitbang.rs        BitBangI2c
│  │  └ sim.rs            SimI2cBus, I2cPinModel, PinLevelI2cSlave
│  └ spi/
│     ├ mod.rs            SpiSlave, VirtualSpiDevice, VirtualSpiBus, CsPolarity
│     ├ bitbang.rs        BitBangSpi (modes 0..=3)
│     └ sim.rs            SimSpiBus, SpiPinModel, PinLevelSpiSlave
└ devices/                building blocks for models
   └ register.rs          bus-independent RegisterMap, SpiFormat / I2cFormat
examples/
├ register_map.rs         attach a register-list model to virtual I2C and SPI buses
├ pin_level.rs            drive the signal lines with bit-bang masters
└ mcp23017/               write an IC model and drive it with mcp23017-driver from crates.io
   ├ main.rs
   └ model.rs             the MCP23017 model (implements I2cSlave)
tests/
└ mcp23017.rs             tests for the example model
```

Crate building blocks live only in `bus` and `devices`. Models of specific ICs live in examples and tests.

## How it works

### Two paths

- **Transaction level**: `VirtualI2cBus` / `VirtualSpiDevice` hand the driver's reads and writes to the model
  (`I2cSlave` / `SpiSlave`) byte by byte. No signal lines are simulated, so it is fast
- **Pin level**: `BitBangI2c` / `BitBangSpi` drive the signal lines on top of `OutputPin` / `InputPin` / `DelayNs`.
  `SimI2cBus` / `SimSpiBus` hold the line levels and the simulated time (in ps); `delay_ns` advances the time

`VirtualI2cBus::attach_i2c` attaches a pin-level path as one address on a transaction-level bus
(so Rust models and RTL can share a bus).

### Pin-level models

`I2cPinModel` and `SpiPinModel` have the same shape.

- `set_inputs` is called whenever a line changes. Circuits clocked directly by SCL / SCK evaluate here
- Circuits running on a system clock return `period_ps` and get `tick` once per period
- `set_time_ps` is called whenever the simulated time moves, before any `set_inputs` / `tick` at the new time.
  It does nothing by default; models that dump waveforms use it as their timestamp

### Resolving the lines

- **I2C**: SCL / SDA are open-drain (low if anyone pulls them low). When one model pulls SDA, the other models'
  inputs change too, so `set_inputs` is redelivered until the line levels settle
- **I2C DUTs without an output enable**: models whose `wants_external_sda()` is true get the SDA level driven by
  everyone else. For models that resolve the line inside a Verilog wrapper
- **SPI MISO**: reads 1 when nobody drives it. Two or more drivers at once are counted as contention (`contentions`)

### SPI chip select

- **Polarity**: `add_device_with` accepts `CsPolarity::ActiveHigh`. Models always get a logical `cs_n`; the bus
  converts it. Wrap the CS pin in `InvertedPin` before handing it to `ExclusiveDevice` or a driver
- **CS high time**: pin writes take no simulated time, so the bus leaves a gap between frames
  (`SimSpiBus::set_cs_high_ns`), as a real master does. Without it, `ExclusiveDevice` would deselect and select
  at the same moment, and a slave that synchronizes CS to a system clock would see all frames as one.
  `master()` sets the gap to one SCK period; if you build a `BitBangSpi` from the pins yourself, call
  `set_cs_high_ns`
- **t_CSH**: `SimSpiBus::set_min_cs_high_ns` checks the minimum time between deselecting and selecting again.
  If it is too short, it is counted as a violation and the bus waits for the rest. Frames work without it;
  use it to check that a driver meets a datasheet t_CSH longer than one SCK period (assert that
  `cs_high_violations()` is 0)
